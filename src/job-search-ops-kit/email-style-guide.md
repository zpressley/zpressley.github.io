# Style Guide for Externally-Facing Output

This covers the visual and writing rules for anything this system sends
outside the Notion workspace itself, like a status email, not just the
daily digest. Reusable for any similar output this kind of system
produces.

## Palette

Black text on white background only. No color anywhere: no colored text,
no tinted backgrounds, no colored callout boxes. If something needs
emphasis, that's what bold text and rule lines are for, not color.

## Typography

One serif moment for a single masthead heading, if there is one.
Everything else, including body text, section headers, dates, and any
closing note, stays in a plain system sans-serif. Don't mix fonts beyond
that one deliberate exception.

## Section headers

Uppercase, bold, modest letter-spacing, sitting on a solid bottom rule.
No background shading, no icons, no emoji.

## Rules and dividers, and nothing else

A heavier rule under a masthead if present, a lighter rule under each
section header, a rule above any closing element. That's the entire
visual vocabulary: no boxes, no cards, no shadows, no rounded corners.

## Emoji: internal only

An internal working page (something the automation and the person both
read and edit together) can use emoji freely as visual anchors. Anything
sent externally, even if it's still going to the same person, should
read as if it could be forwarded to someone else without adjustment. No
emoji there.

## Prose over bullets

Flowing short paragraphs with a bold lead-in phrase, separated by clear
breaks, read better than a wall of bullets for narrative content. The
one exception is a genuine action list meant to be scanned and checked
off, which should stay a plain, unstyled list.

## Specificity over vagueness

Always name the actual names and companies involved. "A recruiter
followed up" is not acceptable if the real name and company are known.
The reader should be able to act on the output without needing to open
anything else to get context.

## Precision over collapsing categories

If the underlying data has a real funnel or specific categories, report
them by their actual name rather than collapsing everything into one
generic bucket. If a schema distinguishes between stages, an automated
summary should respect that distinction, not flatten it for brevity.

## A closing element, if there is one

Keep it short, genuinely relevant to the day's content rather than
generic, and sourced from whatever the person has actually said they
want (see the quote-sourcing note in `daily-digest-automation.md`).
Don't default to something arbitrary if they haven't specified a
preference; ask, or skip it.

## Subject line pattern

Keep a consistent, predictable subject line format across every send
(the same title plus the date), so messages thread and sort predictably
in an inbox rather than each one reading like a one-off.
