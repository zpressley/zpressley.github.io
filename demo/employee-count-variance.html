Employee count variance: try it

Three enrichment sources give three different headcounts for the same company. These are 11 real enterprise accounts and the actual numbers each source returned. Move the thresholds and watch which rows get resolved automatically, which ones escalate to a paid AI research step, and what that costs.

Why this matters more than it sounds

Employee count drives segment. Segment drives which rep owns the account. A source that is wrong by an order of magnitude does not produce a slightly wrong report, it hands the account to the wrong team. The row to watch is Clayton Homes, where one source returns its parent company's headcount instead of its own.

What the logic does

For each account it takes the three counts, measures the spread as (max − min) / max, and if that spread is above the first threshold it drops the single source furthest from the median and measures again. The second number is what you can actually trust.

Across these 11 accounts the raw spread averages 65%. After dropping one source per row it averages 20%. That gap is the whole argument for doing this: two thirds of the apparent disagreement is one bad source per row, not genuine uncertainty.

The second threshold decides what happens to rows still in disagreement after the drop. Those go to an AI research step that reads the company's own filings and profiles and returns a standalone headcount with its sources. It costs 3 credits a row. Running it everywhere costs 33 credits on this batch. Running it only where the surviving sources still disagree costs 3, and resolves the row that actually mattered.

That gating is the cheap part. The expensive lesson is in the next section.

The thing I got wrong

I built this expecting the exclusion step to produce the answer. It doesn't. It produces a shortlist.

Turn the gate off so the research step runs on every row, and watch Unilever. The heuristic throws out HG Insights as the outlier. The AI then goes and reads Unilever's 2025 annual report and returns 96,092, which is HG's number exactly. The two sources that survived the exclusion were both inflated. The mechanical logic threw away the correct answer and kept the two wrong ones.

Amazon does the same thing more quietly, landing near the excluded figure rather than the surviving pair. Clayton Homes does a third version: after correctly dropping the parent company count, both survivors were still too low.

So the outlier flag is a triage signal, not a verdict. It is good at telling you which rows to investigate and has no idea which source is right. That is what the third slider is for. It compares the AI result against the surviving cluster and flags anything that disagrees by more than the gap you set. At 30% it surfaces Clayton Homes, Unilever, Amazon, and Alphabet, which is every row on this batch a human should actually look at.

Watch Clayton Homes

It is the row the pipeline exists for. Every source disagrees, and one returns 387,800, which is Berkshire Hathaway's headcount rather than Clayton's. The AI comes back with 8,652 and shows its work: it found a 22,000+ figure on the careers site and rejected it as the broader Clayton enterprise rather than Clayton Homes itself.

Pull the escalation threshold up past 85 and watch it stop firing. That is what a too-conservative gate costs you.

Alphabet is a real failure, not a demo prop

The AI returns 2,164 for Alphabet Inc., a company with roughly 180,000 employees. It ran without a confirmed domain, so the sources may each have resolved a different company of the same name. It is left in because a batch report that hides its one bad row is not a batch report. The fix is to refuse to return a count when domain and LinkedIn URL are both unconfirmed, rather than answering from the name alone.
