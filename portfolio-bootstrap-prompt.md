# Portfolio Bootstrap Prompt

Paste this whole block into a Claude session. It walks through interviewing you,
writing honest case studies, building a static site with no framework, and
publishing it free on GitHub Pages.

A working reference implementation is public at
https://github.com/zpressley/zpressley.github.io if you want to see the finished
shape before you start.

---

## Instructions for Claude

You are helping someone build a portfolio site. Work through the phases in order.
Do not skip Phase 1 or Phase 2. Those are the parts that keep the site honest and
readable, which is the whole difference between a portfolio that survives a
follow-up question and one that doesn't.

### Phase 0: Interview

Ask these before writing anything, one or two at a time rather than as a wall:

1. What do you do, in the words you'd use out loud to a peer?
2. Who is reading this? A hiring manager in your field, a recruiter who doesn't
   know the domain, a potential client? Write for that person.
3. What are three to six projects worth showing? Include work that never
   shipped, side projects, and take-home exercises. Those are often the best
   material because you can describe them freely.
4. For each one: what was broken, what did you build, what changed? If they
   can't answer the third part for a project, that's fine, say so on the page.
5. Do you have artifacts? Screenshots, source code, a deck, a written brief, a
   live URL. Anything a reader can click beats anything you assert.
6. Is any of it confidential? See Phase 2.

Ask for a writing sample too: a Slack message, a newsletter post, an email they
sent. You'll use it in Phase 5.

### Phase 1: The honesty rules

These are not optional and they are the reason to bother.

- **Never invent a number.** No made-up percentages, no "improved efficiency by
  40%." If they didn't measure it, the page says what was built and stops.
- **Unlaunched work gets labeled unlaunched,** in a callout near the top, not a
  footnote at the bottom. "Built, scheduled to go live, never ran in production,
  so there are no measured results" is a strong sentence. It reads as someone
  who knows the difference between design and outcome.
- **When two sources disagree, flag it, don't resolve it.** If a resume says one
  thing and a project doc says another, ask which is true.
- **A gap is content.** "The screenshots didn't survive" or "I can't demo this,
  I lost the files" is honest and costs nothing. Quietly implying otherwise is
  what costs.

Say this back to them plainly: the goal is a site where every claim survives an
interviewer asking "tell me more about that."

### Phase 2: Confidentiality

Name employers. That's how a reader attributes the work, and it's what a resume
does anyway.

Do not publish the employer's internals. Specifically: pricing, rate cards,
margins, tier structures, customer names, customer performance data, credentials,
internal URLs, or anything a legal team would recognize as commercial.

If a project is *about* one of those things, describe the mechanism and change
the numbers, then say on the page that the figures are illustrative. A reader
learns just as much from the design, and the person keeps their reputation.

Before publishing anything from a file they hand you, grep it for names, emails,
phone numbers, API keys, and workspace IDs. If it's a zip, look inside the zip.
A folder-level search does not see into an archive.

### Phase 3: Build the site

Plain HTML, one stylesheet, minimal JavaScript, no framework and no build step.
The reason is maintenance: a portfolio someone updates twice a year should still
work in two years without a dependency upgrade.

```
index.html              home: hero, work grid, about, contact
projects/
  _template.html        copy this per case study
  <slug>.html
assets/
  css/style.css         all styling, colors as CSS variables at the top
  js/main.js            theme toggle and filtering only
  img/                  screenshots, and og/ for social cards
  files/                resume PDF and downloads
.nojekyll               tells GitHub Pages to serve files as-is
.gitattributes          `* text=auto eol=lf` so Windows doesn't churn line endings
```

**Write the project cards as plain HTML in `index.html`, not generated by
JavaScript.** This matters more than it sounds. Search engines and LinkedIn link
previews do not run JS, so a JS-rendered grid means a crawler sees an empty
"Selected work" section. Let JS handle only filtering and the theme toggle, and
have it read the cards already in the DOM.

Each case study page follows the same shape:

1. **Lede.** Two or three sentences: what it is, and the tension in it.
2. **Facts row.** Role, timeline, stack, status. Scannable in two seconds.
3. **Buttons**, if there's something to click: a live demo, the source, a PDF.
4. **The problem.** What was broken and what it cost.
5. **What I built.** The approach, and the decisions worth explaining.
6. **Decisions worth defending.** The reasoning a peer would argue with.
7. **What changed**, or what it was built to do if it never ran.

### Phase 4: Make something clickable

This is the highest-leverage thing in the whole build.

If a project involved an algorithm, a model, a calculation, or a decision rule,
reimplement a small honest version that runs in the browser as a static page.
A hiring manager who clicks a slider and watches a number resolve understands
the work in ten seconds. No paragraph competes with that.

Two rules:

- **Don't fake the parts you can't run.** If half the system needs a model that
  won't fit in a page, say so in a callout and demo the half that does. Make the
  limitation the exhibit: show what the simple version gets wrong, and explain
  that this is exactly why the harder half exists.
- **Use illustrative data if the real data is confidential,** and label it.

If there's no algorithm, the equivalents are a screenshot with a caption pointing
at the specific thing to notice, a hosted deck, or the source in the repo.

### Phase 5: Voice

Draft toward the writing sample from Phase 0. If there isn't one, ask for one.
Without it you will write in your own default register and it will read as
generated, because it is.

Rules that hold regardless of sample:

- **No em-dashes.** This is the single most recognizable tell in AI writing.
  Use a period, a comma, a colon, or a parenthetical. Then grep the finished
  files for the character and confirm zero.
- **First person, and sequential.** "The first thing I tried was X. That worked
  until Y. So I changed it to Z." Not "the system normalizes names, then two
  measures run." A portfolio is a story about a person making decisions.
- **No aphoristic one-liners** as section punctuation. "The banding is the whole
  design." reads as ad copy. Fold the point into the surrounding sentence.
- **Don't end paragraphs by zooming out** to a universal takeaway. Stop on the
  concrete fact and move on.
- **Vary sentence length genuinely.** Some sentences of four words, some of
  thirty-five. Uniform medium-length sentences are their own tell.

When the draft is done, read each page and change a few sentences to things the
person would actually say out loud. Nothing else closes the gap.

### Phase 6: Social cards

Every page needs its own, or a shared link unfurls as a blank box.

Render a 1200x630 PNG per page and add `og:title`, `og:description`, `og:image`,
`og:url`, and `twitter:card` to each page's `<head>`. **The URLs must be
absolute.** Crawlers do not resolve relative paths, and this fails silently.

Put the tags in the template so future pages start with them.

### Phase 7: Publish

GitHub Pages, free, no account beyond GitHub:

1. Create a repo named exactly `<username>.github.io`.
2. Push the site to `main`.
3. Settings, Pages, deploy from branch `main`, folder `/ (root)`.
4. It's live at `https://<username>.github.io` in about a minute.

Set git identity first or the first commit fails with "Author identity unknown":

```bash
git config --global user.name "Their Name"
git config --global user.email "verified@email.com"
```

Use an email verified on their GitHub account, or commits won't link to the
profile.

### Phase 8: Verify before calling it done

Do not trust that it worked. Check:

- Every internal link and asset returns 200, not 404.
- No horizontal overflow at 360px wide. Phones are most of the traffic.
- The page still renders with JavaScript disabled, and the project cards are
  visible. This is the crawler test.
- Zero em-dashes. Grep the files for the character and confirm the count is 0.
- Every `og:image` URL actually resolves.
- Any demo still computes the right answer after edits.

Then load the live URLs, not the local files. A deploy can lag.

### Gotchas that cost real time

- **LinkedIn caches previews hard.** After changing a social card, run the URL
  through LinkedIn Post Inspector or the old empty box keeps showing.
- **Fetching a page you just changed can return a cached copy.** Add a query
  string to bust it before concluding the deploy failed.
- **GitHub renders a repo directory nicely.** Linking source at
  `github.com/<user>/<repo>/tree/main/src/<project>` is a better reading
  experience than a zip download, and Google Drive links usually hit a sign-in
  wall for anyone who isn't already shared in.
- **Windows and line endings.** Add `.gitattributes` with `* text=auto eol=lf`
  or every file will look modified on every checkout.
