SFDC Account Matcher

Company lists kept arriving with no reliable way to check them against Salesforce. I built a matching tool that returned ranked candidates with a confidence score instead of a flat yes or no, so a reviewer could see how good the match actually was before acting on it.

The problem

Partner lists, event lists, campaign lists. They arrived constantly, and every one of them raised the same question: which of these are already accounts in Salesforce? A plain text match answered it badly. Name variants, abbreviations, and legal suffixes broke it on the easy cases. Parent/subsidiary structure broke it on the hard ones. A row for BNSF Railway needs to resolve to the Berkshire Hathaway account, and no amount of string comparison will ever get there.

Underneath that was a constraint I couldn't design around: no Salesforce API access. Not during the Clay trial, not on the base tier, not at any point. Whatever I built could not be a live lookup.

Two engines, and a third mode

  • Fuzzy string matching (rapidfuzz) for close textual variants: abbreviations, legal suffixes, formatting differences. This is what handles NTT DATA against NTT Data Corporation.
  • Semantic matching via a local sentence embedding model (all-MiniLM-L6-v2, running on torch) for names that are related without being textually similar. Embeddings for the whole account export are computed once and cached, then everything is scored against that matrix at once. This is the half that catches parent and subsidiary pairs.
  • Hybrid, which is the one worth using. Semantic runs first, and the names it didn't match fall through to fuzzy. The expensive engine goes first and the cheap one sweeps up behind it, instead of running both across everything and reconciling afterward.

Confidence, not verdicts

I had every input come back with its top three candidates instead of one answer. Each candidate carried a name-similarity score and a domain-match score, blended into a single combined figure, then banded for triage:

BandScoreWhat happens to it
High90%+Trusted directly
Medium75–89%Worth a spot check
ReviewBelow 75%Flagged for a human

A binary matcher fails silently in two directions. It creates duplicate accounts when it's wrong, and it drops real matches when it's cautious. Ranked candidates with a visible score turn both of those into a short queue somebody can work through in a few minutes.

Contacts work differently

Contacts have an actual identifier, so instead of one scorer the contact side runs a priority cascade. An exact email match comes first, and the name is then used to validate that match. A matching email whose name disagrees is a flag worth catching. Only when email fails does it fall back to fuzzy name matching, above a threshold the user sets.

The fallback doesn't score against every contact in the export, either. An inverted index of name words narrows the field to a small candidate set first, and fuzzy matching runs only on that. That's what keeps it usable against a full contact export instead of a sample.

Every result carries the method that produced it: Email + Full Name (98%), Name Only - Flexible (87%). A reviewer can see why something matched, not only how well.

Why it was an app

Packaged as a local Streamlit app instead of a notebook or a one-off script, so teammates without a Python environment could upload a CSV and get scored output back without touching code. It became a standing step in how incoming lists got handled, which a script sitting in someone's home directory never would have.

The constraint that shaped it

No API meant batch, running against periodically exported account data. That was forced, not chosen. With API access this is a different and much simpler piece of software: you look the account up and you have your answer. Without it, everything above exists to get a trustworthy answer out of a file that was already out of date when it was downloaded.
